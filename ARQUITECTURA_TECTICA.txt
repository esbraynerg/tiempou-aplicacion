# 1. OBJETIVO DEL PROYECTO

Construir el código fuente completo de TiempoU, una aplicación de gestión y planificación académica dirigida a estudiantes que deben organizar sus actividades universitarias y administrar su tiempo disponible.

El proyecto debe implementar las funcionalidades, reglas de negocio, cálculos, pantallas, componentes visuales y procesos que fueron definidos y aprobados durante el diseño funcional de TiempoU.

El resultado será un repositorio organizado, modular, documentado y funcional, preparado para su almacenamiento y control de versiones en GitHub.

No se busca desarrollar una infraestructura empresarial ni una aplicación con servicios externos.

# 2. TECNOLOGÍAS

Se utilizarán las siguientes tecnologías:

- React: construcción de la interfaz y sus componentes.
- JavaScript: lógica funcional y operaciones.
- CSS: estilos, distribución y diseño visual.
- HTML: estructura base de la aplicación.
- Vite: herramienta de configuración y ejecución del frontend.
- GitHub: almacenamiento y control de versiones del código.

No se utilizarán TypeScript, bases de datos ni servicios de backend en esta versión.

# 3. ALCANCE DEL PROYECTO

TiempoU será una aplicación frontend funcional.

Incluirá:

- Gestión de materias.
- Gestión de actividades.
- Sistema de priorización IPA.
- Protección de urgencia.
- Dos modalidades de calificación.
- Registro de entregas y calificaciones.
- Historial académico.
- Configuración de disponibilidad semanal.
- Generación de sesiones de estudio.
- Seguimiento de sesiones.
- Cálculo del progreso académico.
- Notificaciones internas.
- Navegación entre pantallas.
- Formularios y ventanas emergentes.
- Datos de demostración precargados.

No incluirá:

- Registro de usuarios.
- Inicio de sesión.
- Contraseñas.
- Autenticación.
- Base de datos.
- Servidores.
- API externa.
- Almacenamiento permanente.
- Sincronización entre dispositivos.
- Pagos.

# 4. MODELO DE DATOS Y ALMACENAMIENTO

La aplicación manejará información global durante la sesión.

Los datos se cargarán automáticamente desde un conjunto inicial de demostración.

Se utilizará un estado centralizado en memoria para compartir la información entre las diferentes páginas y componentes.

Reglas:

1. Los datos iniciales deben ser coherentes entre sí.
2. Las materias tendrán actividades relacionadas.
3. Las actividades tendrán fechas y horas de entrega, esfuerzos, valores académicos y estados.
4. Las actividades conservarán identificadores únicos y relaciones con sus materias.
5. Las sesiones estarán relacionadas con sus actividades.
6. Las notificaciones estarán relacionadas con los eventos que las originan.
7. Las operaciones deben actualizar el estado central.
8. Los cambios deben reflejarse en todas las pantallas correspondientes.
9. Al recargar o cerrar la aplicación, los cambios se perderán.
10. Al iniciar nuevamente, se cargarán los datos iniciales.

No se utilizará localStorage, sessionStorage, IndexedDB ni otro mecanismo de persistencia.

El estado central será la única fuente de información de las entidades principales. Las páginas y componentes no deberán mantener copias independientes de materias, actividades, sesiones o notificaciones.

# 5. ARQUITECTURA GENERAL

La aplicación tendrá una arquitectura modular.

Cada archivo tendrá una responsabilidad específica.

Se evitará:

- Duplicar cálculos.
- Repetir reglas de negocio.
- Crear estructuras de datos diferentes para una misma entidad.
- Colocar toda la lógica dentro de los componentes visuales.
- Crear dependencias circulares.
- Mantener cálculos independientes para cada pantalla.
- Mantener información académica duplicada en diferentes componentes.

La lógica académica estará separada de la interfaz.

Los componentes visuales solicitarán operaciones a través del estado central y los servicios correspondientes.

Los cálculos se realizarán mediante funciones compartidas ubicadas en `lib`.

Los servicios coordinarán las operaciones, validaciones y actualizaciones del estado.

# 8. REGLAS FUNCIONALES QUE DEBE RESPETAR EL CÓDIGO

## 8.1. Priorización IPA

El sistema utilizará la fórmula aprobada:

IPA = 0.35U + 0.20P + 0.45R

Donde:

U = Urgencia.  
P = Peso académico.  
R = Presión del esfuerzo.

Los porcentajes representan:

- Urgencia: 35 %.
- Peso académico: 20 %.
- Presión del esfuerzo: 45 %.

U, P y R tendrán valores entre 0 y 100.

La fecha y hora de entrega serán obligatorias y se utilizará el formato `YYYY-MM-DDTHH:mm`, interpretado en la hora local del dispositivo.

La urgencia se calculará considerando el tiempo restante hasta la fecha y hora de entrega y respetando los intervalos aprobados en la especificación del motor IPA.

El peso académico deberá respetar la modalidad de calificación y los valores permitidos para la materia.

El esfuerzo tendrá en cuenta el tiempo estimado de realización y la disponibilidad configurada.

La presión del esfuerzo se calculará mediante:

R = min(E / D, 1) × 100

Donde:

- E = esfuerzo estimado restante de la actividad.
- D = horas disponibles antes de la fecha y hora de entrega.

Si no existen horas disponibles, se aplicará el valor de contingencia aprobado:

D = 0 y R = 100.

La ausencia de disponibilidad no debe impedir el funcionamiento de la aplicación. En ese caso, no se generarán sesiones de estudio.

### Protección de urgencia

La clasificación deberá respetar las reglas aprobadas:

- Una actividad que vence hoy tendrá prioridad sobre otra que vence mañana, aunque su IPA sea menor.
- Una actividad que vence en un día conservará prioridad frente a otra que vence en tres días.
- Cuando exista una diferencia de al menos tres días, los demás factores podrán adquirir mayor relevancia según las reglas aprobadas.

El resultado será una lista general de actividades ordenadas por prioridad.

Los empates no deberán generar errores y conservarán el orden de registro.

La implementación deberá respetar los ejemplos de validación aprobados y no inventar una fórmula alternativa.

## 8.2. Modalidades de calificación

Solo existirán dos modalidades.

### MODALIDAD 1: ACUMULACIÓN DE PUNTOS

La materia tendrá:

- Puntaje máximo.
- Puntaje mínimo para aprobar.
- Actividades ordinarias con valores individuales.

El sistema calculará:

- Puntos obtenidos.
- Puntos perdidos.
- Puntos restantes.
- Porcentaje de progreso.
- Resultado académico.

La suma de los valores de las actividades ordinarias deberá corresponder al total configurado para la materia.

Las actividades de puntos extra se identificarán por separado y no modificarán el total base ni el porcentaje de progreso ordinario.

### MODALIDAD 2: PROMEDIO DE CALIFICACIONES

Las actividades utilizarán la misma escala de calificación de la materia.

Ejemplos de escalas:

- 0 a 5.
- 0 a 10.

El promedio se calculará mediante la media aritmética simple de las actividades calificadas que correspondan.

Las actividades Entregadas pendientes de calificación no se incluirán en el promedio hasta que tengan una nota registrada.

Las notas superiores al máximo permitido o inferiores a cero deberán rechazarse.

La modalidad de calificación quedará bloqueada después de crear la materia.

Los valores y las calificaciones individuales podrán modificarse cuando las reglas funcionales lo permitan.

Los cálculos se actualizarán automáticamente.

## 8.3. Estados de las actividades

Las actividades tendrán tres estados principales:

PENDING:

Actividad que todavía no tiene un resultado definitivo de entrega y permanece en la lista de pendientes.

DELIVERED:

Actividad marcada como Entregada. Pasa al historial y puede encontrarse pendiente de calificación o calificada.

NOT_DELIVERED:

Actividad marcada como No entregada. Se registra con calificación de cero y participa en los cálculos académicos correspondientes.

**Pendiente de calificación no es un estado independiente de la actividad.**

Es una condición de presentación de una actividad cuyo estado continúa siendo DELIVERED y que todavía no tiene una calificación registrada.

Reglas:

- Una actividad vencida no se convierte automáticamente en No entregada.
- Una actividad Entregada sin nota no debe contabilizarse todavía en los resultados académicos.
- Borrar una nota no cambia el estado DELIVERED.
- Borrar una nota mantiene la actividad en el historial como Pendiente de calificación.

### Reactivación

Al reactivar una actividad desde el historial:

- Se elimina la calificación registrada o el cero anterior.
- El estado vuelve a PENDING.
- La actividad regresa a la lista de pendientes.
- Vuelve a participar en la priorización IPA.
- Se excluye temporalmente de los cálculos académicos hasta registrar un nuevo resultado definitivo.
- Puede recibir una nueva planificación de sesiones si existe disponibilidad.

La reactivación no equivale a borrar una calificación.

## 8.4. Estados de las materias

Las materias podrán encontrarse:

- En curso.
- Finalizadas.

Una materia solamente podrá finalizarse cuando todas sus actividades tengan un resultado de entrega registrado: DELIVERED o NOT_DELIVERED.

Una actividad DELIVERED pendiente de calificación no impide finalizar la materia.

Las materias finalizadas se mostrarán en la pestaña Finalizadas y sus actividades seguirán siendo consultables.

Se permitirá reactivar materias conservando sus datos y estados anteriores.

Si se reactiva una actividad perteneciente a una materia finalizada, la materia regresará automáticamente a En curso.

Al eliminar una materia se eliminarán también sus actividades y registros asociados.

Al eliminar una actividad se eliminarán sus sesiones y registros asociados.

## 8.5. Disponibilidad semanal

La disponibilidad se configurará por días de la semana y mediante intervalos horarios.

El estudiante ingresará sus horas disponibles, sin necesidad de registrar separadamente sus horarios laborales o de clases.

Se permitirán varios intervalos por día, siempre que no existan horarios inválidos o solapamientos.

Los cambios se aplicarán al guardar la configuración.

No se realizarán recálculos completos de la planificación mientras el estudiante todavía esté editando los intervalos.

### Límites de estudio

Existirá un límite general de horas de estudio por día.

Este límite representa el máximo global permitido para la suma de las sesiones de todas las actividades durante un mismo día.

Cada actividad podrá tener un límite diario particular inferior al límite general.

El límite particular nunca podrá permitir superar el límite global.

## 8.6. Planificación de sesiones

El sistema podrá distribuir las actividades en sesiones de estudio.

Reglas:

- Se respetará la disponibilidad configurada.
- Se tendrá en cuenta el esfuerzo estimado restante.
- Se respetará el límite general diario.
- Se respetará el límite particular de cada actividad cuando exista.
- Se permitirá modificar el número de sesiones.
- Se recalculará la distribución cuando corresponda.
- El estudiante podrá marcar una sesión como realizada desde el detalle de la actividad.
- El seguimiento se realizará mediante una ventana emergente o modal.

### Conservación y reorganización

Cuando cambie la planificación:

- Las sesiones realizadas deben conservarse.
- Solo se reorganizarán las sesiones pendientes.
- No se deben duplicar sesiones realizadas.
- El esfuerzo restante debe considerar el tiempo ya invertido.
- La nueva planificación debe utilizar el esfuerzo restante y los días disponibles antes de la entrega.
- Si no existe tiempo disponible suficiente, se debe informar al estudiante sin modificar el esfuerzo estimado.

Cuando una actividad se marque como Entregada o No entregada, dejará de generar sesiones futuras.

Si posteriormente se reactiva, podrá recibir una nueva planificación utilizando el esfuerzo restante y conservando las sesiones realizadas.

Si no existe disponibilidad configurada, la aplicación seguirá funcionando, pero no generará sesiones.

## 8.7. Notificaciones

Las notificaciones serán internas y simuladas.

Se contemplan únicamente dos tipos:

1. Entregas próximas: se generan 24 horas antes de la fecha y hora de entrega.
2. Sesiones próximas: se generan 30 minutos antes del horario programado.

Reglas:

- Las notificaciones funcionarán únicamente mientras la aplicación permanezca abierta.
- No se implementarán procesos en segundo plano.
- No se mostrarán notificaciones atrasadas al volver a abrir la aplicación.
- Se evitarán avisos duplicados para un mismo evento.
- Los cambios de fecha, hora o planificación actualizarán las notificaciones correspondientes.
- No se generarán notificaciones de entrega para actividades Entregadas o No entregadas.
- No se generarán notificaciones para sesiones realizadas, eliminadas o reorganizadas.

No se implementarán notificaciones push, correos, SMS ni servicios externos.

# 9. COMUNICACIÓN ENTRE LOS MÓDULOS

La comunicación seguirá este principio:

INTERFAZ → ESTADO CENTRAL / OPERACIONES → SERVICIOS → LIB → ACTUALIZACIÓN DEL ESTADO CENTRAL → INTERFAZ ACTUALIZADA.

Ejemplo:

Cuando el estudiante crea una actividad:

1. El formulario recoge los datos.
2. La operación correspondiente solicita la creación al servicio de actividades.
3. activityService valida los datos mediante las funciones correspondientes.
4. Se consulta la lógica de cálculo de `lib` cuando sea necesario.
5. Se actualiza el estado central.
6. Se recalculan la prioridad y la planificación afectadas.
7. Se actualizan las notificaciones relacionadas.
8. Las páginas y componentes reciben los datos actualizados.

Ninguna página deberá mantener una copia independiente de las materias o actividades.

Las operaciones que afecten a varias entidades deberán mantener sus relaciones y estados coherentes.

# 14. CONTROL DE VERSIONES

GitHub será el repositorio principal del proyecto.

Cada entrega deberá identificar:

- Nombre del archivo.
- Ruta correspondiente.
- Versión.
- Funcionalidad implementada.
- Archivos relacionados.
- Dependencias necesarias.

Cuando se modifique un archivo existente se entregará su versión completa y se identificarán los módulos que podrían necesitar actualización.

No se considerará terminada una funcionalidad hasta comprobar su integración con las demás.
